# Why it is compiled in

*One of the elvboot articles. It answers the question every reader of
the tutorial asks at some point: why does a change of policy mean a
rebuild of the loader? Why not a configuration file?*

## The two places a decision can live

A boot loader that judges the platform needs to know what to expect:
which firmware hash is the right one, which key store, which partition
tables, which gates to run in which phase and what to do when one
fails. There are two places for that knowledge. It can be read at boot
from a file on the medium, or it can be part of the signed binary.

Most systems that judge at boot choose the file: a policy in
`/boot/loader.conf`, a list of hashes in a text file, a configuration
database. It is the obvious choice, because changing a text file is
cheap and rebuilding a loader is not. elvboot chooses the binary for the
decisions that matter, and the file for the values that may move. The
rest of this article is about where the line runs and why.

## What a file on the medium is worth

Secure Boot verifies the loader binary against the owner's key in the
firmware's `db`. It verifies nothing else. A configuration file beside
the loader is protected by whatever the loader does with it, and a
loader that reads its own rules from an unsigned file has rules that
anyone with the medium can edit: remove a gate, change an expected
hash, flip the reaction from halt to proceed. The whole point of the
measurement, that the owner declared what the platform should look
like, evaporates if the declaration is one `vi` away.

FreeBSD has an answer for files, the manifest: libsecureboot verifies
every file it loads against a signed list of hashes, and elvboot uses it
(`stage manifest`, `stage attest`, the `PreloadVerified` claim). One
could put the policy in a manifest-covered file and be done. elvboot
does put the *values* there: the expected PCR bank, the witness
receipts, the question text, the rescue target, the time windows, all
live in `loader.trust.conf`, a file in the signed manifest. A relearn
after a firmware update is a new conf and a push, no rebuild.

The *structure* is not there. Which claims exist, which gates they form,
which policies fire which actions in which phase, and the baselines of
the machine, the fingerprints of firmware, board and keys: these are C,
generated by elebake and compiled into the loader.

## Three reasons the structure is code

**One source, no drift.** The loader has gates. earlboot, the rc script,
has gates. elvbootd, the daemon with its startup, shutdown and periodic
hooks, has gates. All three must agree on what the owner decided, and
they are written in two languages for three runtimes. If each read its
own configuration, they would drift, and the drift would be found at
the worst moment. In elvboot the three artifacts are *generated from the
same records*: `stage build` renders `foundation.c` from the stage's
bindings first thing, `stage earlboot mk` and `stage elvbootd mk` render
the scripts from the same bindings, and the same expectations, the same
names, the same reactions appear in all three because they were never
written three times. The concept notes compare this to a compiler: the
database is the source, the three artifacts are the object code, and
the test of correctness is a diff of the generated text, not a reading
of three configurations.

**The checker is inside the measured chain.** A loader that reads its
policy from a file is a generic interpreter; what it does on this
machine is in the file. A loader with its policy compiled in is
*specific to this owner's decisions*, and the Secure Boot signature over
it covers those decisions. The PCR 4 the TPM records at boot is the
hash of this loader, so the sealed key file of the disk is bound not
only to "an elvboot loader ran" but to "the loader with these gates
ran". The same is true one level down: the generated earlboot is in the
signed manifest, so the script that classifies the sentinel answer is
itself verified before it runs. Configuration cannot be covered that
way without becoming code, so elvboot lets it become code.

**Decisions leave the C.** The tutorial's chapter 13 says it for the
prerequisites lists, and it is the pattern throughout: the hand-written
C of the loader contains no decision. `foundation.c` in the patch series
is an empty shell with no gates and no policies, so an unprovisioned
tree still links and boots like the stock loader. Every gate, every
binding, every baseline in a real loader came through elebake from a
record in the database, with a name, a time and a dump line. That is
what makes the forensic report possible: "what was required, from which
code, under which keys" is answerable because requirement and code are
the same artifact, and the dump reproduces it. A configuration file
would carry the same information with none of the provenance.

## The price, stated

A rebuild takes minutes and a push. A new gate, a new binding, a new
baseline are a cycle of `stage foundation`, `stage build`, `stage sign`,
`stage include`, `stage push`, and the first boot after a rebuild
learns the new PCR bank (`pcr-learn`) because the loader's hash moved.
The tutorial's chapter 16 is honest about how long the daily cycle is.
The workflows exist because the sequences were typed from memory once
too often: `elebake workflow show rebuild` prints the cycle.

Two things soften it. The line between structure and value is drawn so
that the frequent changes are values: a firmware update, a new card, a
moved inventory set, a relearned witness are all conf and push. And the
machine-specific baselines are a separate generated file, `site.mk`,
rendered from the records as `-D` flags, so the same source tree
produces loaders for different machines, and a baseline change
recompiles without touching the tree.

## Why the loader at all, and not the kernel

The kernel has far better tools for everything the loader does:
drivers, a file system, a shell. Why measure in the loader?

Because the loader is the last code that runs before the disk key
exists. Everything elvboot wants to decide, whether to release the key,
whether to divert to the rescue or the decoy, whether to halt, must be
decided before the key is in memory, or it is not a decision but a
cleanup. The KERNEL phase of the loader runs after the interactive
window has closed and before `ExitBootServices`: the firmware's services
are still there to read EFI variables, talk to the TPM, read the NVMe
SMART log, and the kernel has not been entered. It is the one place
with both the evidence and the power to refuse. What can wait until
after the key exists, the classification of the sentinel answer, the
mail, the report, the shutdown anchor, is in earlboot and elvbootd,
which is why those exist as separate artifacts and not as more loader.

## Why FreeBSD's loader and not a new one

The patch series adds a local layer to the stock EFI loader rather than
replacing it. The loader already has `geliboot`, which derives GELI
keys from passphrase and key files exactly as the kernel does; it has
`libsecureboot` and the manifest; it has BearSSL for HMAC and the
libsa crypto for the record; it has the Lua environment the owner
knows. elvboot adds measurement providers, claims, gates, actions and
policies as a catalog in `stand/efi/loader/local/`, with a few call
sites in the stock code, one per phase. The catalogs are parsed
by elebake from the headers, so a new measurement is born as a patch,
reviewed as C, and appears in `elebake help` without a change to the
tool. A loader of its own would have had to earn each of these pieces
again.

## Why emit shell and not execute

Readers of the tutorial notice that elebake prints shell by default and
runs it only when told. That is the same principle one level up. The
owner is about to let a tool write to an ESP, a TPM, a GELI header, and
the tool's first duty is to show, as text, exactly what it is going to
do. Every command is a function that emits lines; whether the lines run
is a pin per function, and the pins are part of the database, dumped
and restored with it. A compiled script of the whole provisioning, the
dump, is the same text, which is why a database can be replayed on a
second machine and why a rescue system can carry one. The architecture
document explains the three function classes; the reason for them is
here: a boot trust chain that nobody can read as text is a boot trust
chain nobody can audit.
